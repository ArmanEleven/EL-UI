# طرح پیاده‌سازی سیستم چندادمینی EL-UI

> وضعیت: سند طراحی اولیه؛ هنوز کد اجرایی سیستم چندادمینی پیاده‌سازی نشده است.

این سند به فارسی نوشته شده تا مسیر کار قابل‌پیگیری باشد. هدف، ساخت یک سیستم واقعی چندادمینی شبیه قابلیت‌های مدیریتی PasarGuard است؛ نه صرفاً اضافه‌کردن صفحه یا دکمه.

## مانع فعلی در مخزن

در شاخه `main` مخزن EL-UI، در حال حاضر مستندات برنامه‌ریزی و بررسی معماری وجود دارد، اما کد اصلی 3X-UI/EL-UI و فایل‌هایی مثل `go.mod` و مدل‌های پایگاه‌داده در این شاخه موجود نیستند. بنابراین تغییر امن مدل‌ها، API و رابط کاربری تا وقتی کد اجرایی به مخزن وارد یا شاخه توسعه واقعی منتشر نشود ممکن نیست.

کد موجود روی رایانه توسعه‌دهنده ممکن است شامل تغییرات منتشرنشده باشد؛ قبل از ادغام باید اختلاف آن با `main` بررسی شود. این سند عمداً هیچ ادعایی درباره آماده‌بودن قابلیت‌ها نمی‌کند.

## محدوده نسخه اول

### ۱. مالک اصلی (Owner)

- دسترسی کامل به مدیریت ادمین‌ها و نقش‌ها
- ایجاد، ویرایش، غیرفعال‌سازی و حذف ادمین‌های فرعی
- تعیین محدودیت و دسترسی هر ادمین
- مشاهده گزارش رویدادهای مدیریتی

مالک اصلی نباید از طریق رابط عادی ادمین فرعی قابل حذف یا تنزل سطح دسترسی باشد.

### ۲. ادمین فرعی

هر ادمین باید حساب مستقل داشته باشد و فقط عملیات مجاز را انجام دهد. برای هر درخواست، سرور باید هویت و مجوز را بررسی کند؛ پنهان‌کردن گزینه‌ها در رابط کاربری به‌تنهایی کافی نیست.

### ۳. نقش‌ها و محدوده دسترسی

برای هر بخش، مجوزهای جداگانه تعریف می‌شود:

- مشاهده
- ساخت
- ویرایش
- حذف
- عملیات ویژه، مانند بازنشانی مصرف یا تغییر مالک

محدوده داده‌ها:
- **فقط موارد خودش:** ادمین فقط کاربران تحت مالکیت خودش را می‌بیند و مدیریت می‌کند.
- **همه موارد:** فقط در صورت داشتن مجوز صریح.
- **بدون دسترسی:** هیچ داده یا عملیاتی از آن بخش در دسترس نیست.

### ۴. محدودیت‌های ادمین

- حداکثر تعداد کاربران
- سقف ترافیک تخصیص‌یافته و مصرف‌شده
- حداقل و حداکثر حجم مجاز برای هر کاربر
- محدودیت زمان انقضا
- وضعیت فعال، غیرفعال یا محدودشده
- محدودیت‌های اختیاری برای قالب، گروه یا نوع کاربر

همه محدودیت‌ها باید در API و منطق سمت سرور enforce شوند. بررسی‌های مربوط به ظرفیت و ساخت کاربر باید در برابر درخواست‌های هم‌زمان نیز امن باشند.

### ۵. ارتباط با هسته پنل

هسته فعلی پنل مسئول ساخت کانفیگ‌ها، inboundها، پروتکل‌ها و اجرای Xray باقی می‌ماند. لایه مدیریتی باید از رابط مشخص و کنترل‌شده برای اعمال تغییرات استفاده کند؛ از نوشتن مستقیم و بدون کنترل در دیتابیس هسته خودداری می‌کنیم.

## مدل داده پیشنهادی

این مدل مفهومی است و تا بررسی مدل واقعی پایگاه‌داده نباید به‌عنوان migration اجرا شود:

- `admins`: شناسه، نام کاربری، هش رمز، وضعیت، شناسه نقش، سهمیه و مصرف
- `admin_roles`: نام نقش و تنظیمات نقش
- `admin_permissions`: مجوزها و محدوده داده برای هر بخش
- `admin_user_ownership` یا رابطه مالکیت موجود: اتصال هر کاربر به ادمین مسئول
- `admin_audit_logs`: عامل، عملیات، هدف، زمان، نتیجه و فراداده پالایش‌شده

اگر مدل فعلی کاربران از قبل فیلد مالکیت مناسب داشته باشد، پیش از افزودن جدول موازی همان گزینه بررسی می‌شود.

## اصول امنیت و سازگاری

1. رمز عبور فقط به شکل هش امن ذخیره شود؛ هرگز متن خام یا رمز پیش‌فرض ثابت ثبت نشود.
2. مجوزها در سمت سرور و برای هر عملیات بررسی شوند.
3. همه پرس‌وجوهای کاربران به محدوده مجاز ادمین محدود شوند.
4. تغییرات schema با migration نسخه‌دار و قابل‌آزمایش انجام شوند.
5. پیش از migration، پشتیبان قابل‌بازیابی از دیتابیس گرفته شود؛ تست فقط روی دیتابیس آزمایشی باشد.
6. عملیات حساس و تغییرات نقش‌ها ثبت رویداد شوند، بدون ثبت رمز، توکن یا اطلاعات محرمانه.
7. مالک اصلی و روش بازیابی دسترسی نباید با حذف یک ادمین فرعی از بین برود.
8. رابط فارسی، راست‌چین و قابل‌استفاده در نمایشگر موبایل باشد؛ نام‌های فنی ضروری در کد انگلیسی می‌مانند.

## ترتیب اجرا

- [ ] واردکردن یا انتشار شاخه واقعی کد هسته در مخزن و تثبیت نسخه مبنا
- [ ] بررسی مدل‌های دیتابیس، احراز هویت، middleware و APIهای فعلی
- [ ] نهایی‌کردن مدل داده و migration سازگار با دیتابیس موجود
- [ ] پیاده‌سازی سرویس مجوزها و محدودسازی مالکیت در بک‌اند
- [ ] پیاده‌سازی API مدیریت ادمین و نقش‌ها
- [ ] افزودن صفحات فارسی و راست‌چین
- [ ] تست‌های منفی برای دسترسی غیرمجاز و دورزدن سهمیه
- [ ] بیلد و تست روی داده آزمایشی، سپس بازبینی انسانی قبل از ادغام

## معیارهای پذیرش نسخه اول

- ادمین فرعی نمی‌تواند ادمین اصلی را حذف یا نقش خودش را ارتقا دهد.
- ادمین با محدوده «موارد خودش» نمی‌تواند کاربران ادمین دیگر را با تغییر شناسه در درخواست API بخواند یا تغییر دهد.
- ساخت کاربر پس از رسیدن به سقف تعداد یا سهمیه مجاز رد می‌شود.
- کاربر موجود و ورود فعلی پس از migration معتبر باقی می‌مانند.
- تست‌ها شکست‌های مجوز و سهمیه را پوشش می‌دهند.
- هیچ قابلیتی «تکمیل‌شده» اعلام نمی‌شود مگر اینکه کد و تست قابل‌تکرار داشته باشد.
